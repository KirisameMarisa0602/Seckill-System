# V6.0 测试与检验报告 (实现了整体架构升级、用户注册、管理员侧接口以及修复Redis Pub/Sub分布式广播与幽灵售罄问题)

## 1. 测试背景与核心里程碑
在 V5.0 版本完成接口限流、全局异常治理以及 Redis 工程化重构之后，系统的外围安全屏障已经固若金汤。但面向分布式集群部署场景，系统内部存在一个致命的架构级隐患：**JVM 本地内存中的 `ConcurrentHashMap` 售罄标记是单机私有的，一旦商品因为瞬时并发归零，该单机节点上就永久锁死了该商品的抢购通道，即便后台运营紧急补货、或者超时守护进程自动释放库存，这台机器上的用户也永远无法再次下单，我们称之为"幽灵售罄"死锁现象。**

本版本（V6.0）的核心攻坚目标就是彻底歼灭这个分布式高并发世界的著名难题。通过引入 Redis 发布订阅（Pub/Sub）机制实现全节点广播同步，打破单机本地缓存的信息孤岛，达成“库存恢复的那一刻，全网所有应用节点在毫秒级内同步解封，商品满血复活”的工业级最终一致性目标。

## 3. 第二阶段：幽灵售罄歼灭战 (Redis Pub/Sub 广播机制核心攻坚)

这是 V6.0 版本中最具里程碑意义的核心战役。我们人为制造出经典的“售罄死锁”现象，然后利用 Redis 发布订阅机制瞬间破解它。

### 3.1 构造幽灵售罄环境
*   **环境初始化**：我们将两款测试商品的秒杀库存强行调整至极少（如 1 件）。并且清空环境脏数据。
    ![MySQL数据库商品信息抹除](./assets/v6.0-architecture-overhaul/MySQL数据库商品信息抹除.png)
    ![底层数据库库存改为1](./assets/v6.0-architecture-overhaul/底层数据库库存改为1.png)
*   **暴力触发单机售罄死锁**：利用请求强抢最后 1 件商品，将 Redis 的库存清 0。此时 Tomcat 本地 `emptyStockMap` 永久标记商品死亡。
    ![将商品库存设为0模拟售罄状态](./assets/v6.0-architecture-overhaul/将商品库存设为0模拟售罄状态.png)
    后续用户再次请求，被 Controller 层的 Map 拦截器以 `500200 抱歉，库存不足` 秒杀击退。
    ![抢购显示商品不足](./assets/v6.0-architecture-overhaul/抢购显示商品不足.png)
    同时 Redis 中 `isStockEmpty` 售罄标记死死卡住了所有放行通道。
    ![redis同步模拟库存为0](./assets/v6.0-architecture-overhaul/redis同步模拟库存为0.png)

### 3.2 解法一：管理员后台热更新紧急救场（运营补货灭幽灵）
幽灵售罄发生后，假设运营人员第一时间进行后台补单操作。
*   **发起热更操作**：管理员接口传入重置库存信息指令。
    ![测试管理员对商品信息热更新](./assets/v6.0-architecture-overhaul/测试管理员对商品信息热更新.png)
*   **数据层更新确认**：MySQL 底层和 Redis 中的库存记录瞬间受到响应并刷新，售罄标志在 Redis 中被摘除。
    ![热更新MySQL数据库信息同步更新](./assets/v6.0-architecture-overhaul/热更新MySQL数据库信息同步更新.png)
    ![热更新redis库存同步更新](./assets/v6.0-architecture-overhaul/热更新redis库存同步更新.png)
    ![redis中售罄标志消失](./assets/v6.0-architecture-overhaul/redis中售罄标志消失.png)
    管理页面同样模拟确认补货成果。
    ![模拟管理员补货](./assets/v6.0-architecture-overhaul/模拟管理员补货.png)
*   **架构绝杀时刻：全服广播同步瞬发**
    代码触发发布订阅，从控制台日志可以看出，监听器收到了频道消息，并成功清空了 Controller 本地内存的售罄标记！
    ![后台日志表明库存恢复](./assets/v6.0-architecture-overhaul/后台日志表明库存恢复.png)
*   **最终结果验证**：用户的抢购再次发车，原先被“死锁”的商品通道全面复苏。
    ![库存补回到1后再次模拟下单成功](./assets/v6.0-architecture-overhaul/库存补回到1后再次模拟下单成功.png)
    ![库存恢复后成功下单](./assets/v6.0-architecture-overhaul/库存恢复后成功下单.png)

    ![用户下单成功，迟迟不付款等待死信计时](./assets/v6.0-architecture-overhaul/用户下单成功，迟迟不付款等待死信计时.png)
    ![下单成功后开启倒计时（测试定为1min，后续会改），超时订单进入死信队列](./assets/v6.0-architecture-overhaul/下单成功后开启倒计时（测试定为1min，后续会改），超时订单进入死信队列.png)

*   **库表与本地内存的双重自愈**：
    订单状态变为 -1。
    ![成功落库订单记录，订单状态为-1](./assets/v6.0-architecture-overhaul/成功落库订单记录，订单状态为-1.png)

    底层数据库与 Redis 再次完美对应（数量+1）。
    ![库存重新回到1](./assets/v6.0-architecture-overhaul/库存重新回到1.png)
    后续防刷或因其他错误被拦下的操作确保：恶意请求下，真实库存与Redis数据没有任何误减。

## 4. 架构演进总结与通关宣言 (V0.5 -> V6.0 史诗通关)
历经六个重大版本的迭代与跨越，整个高并发秒杀体系今日正式圆满收官：
1.  **V0.5**：直面最原始的数据库裸奔超卖灾难，深刻理解了并发更新覆盖的根源。
2.  **V1.0**：使用 Redis+Lua 原子脚本在内存层面构建了拦洪大坝，彻底杜绝超卖。
3.  **V2.0**：引入 RabbitMQ 异步削峰填谷，斩断了同步羁绊，实现流量尖刺的平滑消化。
4.  **V2.2**：引入 MQ 的 ACK 确认机制与死信队列，赋予金融级物理断电重启后的强数据一致性。
5.  **V3.0**：实现了分布式 Token 鉴权无感解析与一人一单的绝对防御。
6.  **V4.0 & V5.0**：通过多重验证及 AOP 限流控制，消灭了非法路径与极客刷单洪流。
7.   **V6.0**：使用 Redis Pub/Sub 技术重锤砸碎了本地内存“幽灵售罄”的死锁孤岛，打通了微服务多机器状态协同的最后一公里。

从千万流量涌入、洪峰拦截、异步排队、到容灾自愈全链路，这已是一套完全可以独立承接工业级大促、拥有生产就绪形态的硬核电商秒杀底座代码。
